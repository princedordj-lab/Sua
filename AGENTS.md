# Sua — Agent Instructions

Sua ("soo-ah") is an offline-first exam-prep app for African university students: lectures, slides and typed notes become summaries, flashcards and quizzes. There is **no root `package.json` or workspace config** — three independent npm projects, each installed and run from its own directory:

| Path | What it is |
| :--- | :--- |
| `Sua/` | Expo SDK 57 / React Native 0.86 / React 19 app (the product) |
| `backend/` | Express 5 API (JS ESM) + Postgres-backed job runner, Prisma 7 + Neon Postgres, Clerk auth |
| `web/` | Next.js 16.4 web app — marketing landing, `/health`, and the signed-in product under `/app/*` |

Nested instruction files are authoritative for their directory: `Sua/AGENTS.md` (Expo rules — fetch the SDK 57 docs, do not trust memory) and `web/AGENTS.md` (Next.js 16 block, rewritten by `next dev`; commit it rather than reverting). `README.md` is a stale copy of an older AGENTS file — trust this file and the code over it.

## Commands

Mobile (`cd Sua`):
```bash
npx expo install <pkg>   # never npm install for Expo/RN deps — pins SDK-compatible versions
npx tsc --noEmit         # typecheck
npx expo lint            # eslint (eslint-config-expo)
npm run android          # expo run:android — project uses expo-dev-client, so use a dev build
npx expo prebuild        # after app.json/plugin changes; never hand-edit android/ or ios/
```

Backend (`cd backend`):
```bash
npm run dev              # API on :4000 (tsx watch)
npm run dev              # API on :4000 (tsx watch); jobs drain via the tick route
npx prisma migrate deploy   # apply migrations to the Neon dev DB (uses DIRECT_URL)
npx prisma generate         # after schema edits; client goes to gitignored src/generated/prisma
npm run build               # esbuild bundle -> dist/index.js (Vercel build)
npm run eval -- <sample> --kind lecture_note|reference   # prompt/validation harness
npm run eval -- --long [--sections N] [--mock]   # long-file needle/resume/failure/cost eval; --mock = deterministic offline provider (live needs the xkiro quota)
npm run r2:login             # Cloudflare auth for the Android APK bucket (wrangler devDependency, Node >=22)
npm run r2:bucket:create     # create the `sua-downloads` R2 bucket that hosts the APK
npm run r2:domain:add -- --domain dl.<domain> --zone-id <zone>   # connect the public download hostname
npm run r2:upload -- "sua-downloads/android/sua-<version>.apk" --file <path> --content-type application/vnd.android.package-archive
```

Web (`cd web`): `npm run dev`, `npm run build`, `npm run lint`.

There is **no test suite**. Verification is `npx tsc --noEmit` + `npx expo lint` (mobile), `npm run build` (backend/web); for backend-only edits an `npx esbuild <files> --outdir=.tmp --format=esm` parse pass is enough.

## Backend invariants

- Every request-scoped **data** query goes through `withUser(clerkId, tx => …)` (`src/lib/db.js`), which sets `app.current_user_id` inside a transaction for the RLS policies. Gotcha: the Neon role behind `DATABASE_URL` (`neondb_owner`) has **BYPASSRLS**, so the database does not enforce isolation today — the convention does. Use direct `prisma` only for cross-user/infra work (`lib/pipeline.js`, `lib/runner.js`, `lib/extraction.js`, usage counters). Keep external I/O outside `withUser`; its transaction times out after 15s. The one approved exception is the `authenticate` fast path (`middleware/auth.js` → `findUserByClerkId`): answering "who is calling" is a plain `findUnique` keyed by the Clerk id the verified session JWT already carries, because opening a transaction per request just to learn the caller doubled pool demand and made the client's post-sign-in burst surface as `P2028` on `GET /api/me`. Provisioning and every write still use `withUser`, and `ensureUser` single-flights concurrent provisions per Clerk id. That middleware read **is** the row: `identityFromRequest` puts it on `identity.user`, so `requireUser(tx, identity)` answers from it and returns without querying (the in-transaction `findUnique` stays as the fallback for a caller with no preloaded identity, and for the day the role loses BYPASSRLS). One authenticated request therefore spends **one** transaction — re-reading the caller inside it was the sixth round trip that turned `GET /api/notes/course/:id` into a 25 s expired commit.
- `withUser`'s 15s is a budget for **WAN round trips**, not for rows: BEGIN, `set_config`, each statement and COMMIT is a network hop to Neon, so *statements per transaction* is the number that must stay small. Batch reads with `WHERE id IN (…)` instead of looping (`/notes/sync` pre-reads tombstones, notes and owned courses for its chunk), chunk large writes into separate transactions (`SYNC_CHUNK_CHANGES`, and a retried chunk is a no-op because the timestamp guard rejects only *strictly* older writes), and keep `previewFeatures = ["relationJoins"]` in `prisma/schema.prisma`: it makes **every** `include` cost one statement instead of two (measured on the course pull: 1 statement with the flag, 2 without; a two-to-many include is still 1 statement — two `LEFT JOIN`s). Do not write `relationLoadStrategy: "join"` at a call site — it is a per-query override gated on that same generator flag, so a client generated from a schema without it rejects every note read with `PrismaClientValidationError: Unknown argument 'relationLoadStrategy'` (a 500), and the flag already makes joins the default, so the arg buys only a second thing to keep in sync. Same class of coupling as the generator settings below: a query-level arg whose validity comes from schema config is fragile; prefer the config switch that covers all includes and keep the call sites plain (`include: noteInclude`), with the intent stated in a comment. `config/prisma.js` sizes `pg.Pool` on purpose — the adapter forwards its config straight to `pg`, so without `PG_POOL_MAX` (default 5) you silently inherit `max: 10` **per instance**; `connectionTimeoutMillis: 5000` must stay **below** Prisma's `maxWait: 10000` so a saturated pool fails inside the driver rather than orphaning a still-connecting client, and `keepAlive` is what stops Neon autosuspend from dropping the warm sockets between bursts. Capacity failures — `P2028` in either flavour ("unable to start a transaction" / "expired transaction") and the adapter's "timeout exceeded when trying to connect" — are answered **503 + `Retry-After: 5` + `{ error: "SERVER_BUSY" }` from the error handler: retryable and the server's problem, never a 500.
- Migrations are numbered `0_init` … `21_daily_streak`; **next is `22_…`**. No timestamps: Prisma replays directories lexicographically, so `2026…` sorts before `2_notes`. Never edit or rename an applied migration — append a new one.
- Prisma uses a custom ESM client output (`src/generated/prisma`, gitignored). CLI URLs come from `prisma7.config.ts` → `DIRECT_URL`; the running app uses pooled `DATABASE_URL` via `@prisma/adapter-pg`. The generator's `importFileExtension = "js"` is load-bearing for deploys: the files are generated as `.ts`, and both esbuild and Vercel's builder emit `.js` in place, so `.js` specifiers resolve. Setting it back to `"ts"` (which only `tsx` can chase) makes the deployed function die at import with `ERR_MODULE_NOT_FOUND: .../internal/class.ts`.
- Plain JS ESM (`"type": "module"`) — no TS build step. API entry `src/index.js`; jobs run inside the same app via `src/lib/runner.js` (there is no separate worker process). Vercel serves that same file: it auto-detects the Express app from the default export at `src/index.js` and routes every path to it. Do **not** add a `backend/api/` directory — files there claim the `/api` prefix in Vercel's filesystem router, so `api/index.js` answers `/api` exactly and every real route (`/api/health`, `/api/notes/sync`, …) dies with a platform-level `404 NOT_FOUND` before Express runs.
- Public routes are `/`, `/api/health` and the Clerk webhook (mounted before `express.json()` because svix needs the raw body); every other router sits behind `authenticate`.
- Uploads are sign → direct PUT to a short-lived Neon Object Storage URL → complete. `/complete` verifies the object and enforces size, then does **fast intake only**: it marks documents `extractState=pending` and returns — page-wise, resumable extraction (`lib/extraction.js` → `SourceChunk` rows) runs in the background via `waitUntil`, the tick cron, or the client's next status poll. **LlamaParse is the primary parser for DOCX/PPTX and the scan fallback for PDFs** when `LLAMA_CLOUD_API_KEY` is set (`lib/llamaparse.js`; provider state lives on `assets.provider*`, migration `19_llamaparse`): upload → v2 parse → one status check per background pass, never a blocking poll inside a request; a parked parse sets `extractState=pending` + `providerNextPollAt`, and the claim SQL respects that backoff. A PDF only reaches the provider when its local pass found no usable page (or a submitted parse is still parked), so a text PDF never gets a provider call. `cost_effective` is the default tier and is never upgraded automatically; `LLAMAPARSE_FORMATS` decides which formats may use the provider at all (`docx,pptx` keeps every PDF local), `LLAMAPARSE_ENABLED=0` disables the provider. Auth/quota failures are terminal; timeouts, exhausted retries, provider `FAILED/CANCELLED`, `413`, and empty results fall through to the paths below. **PDFs are local-first**: `pdf-parse` reads the embedded text layer per page (page numbers preserved, whitespace normalized conservatively by `lib/page-text.js`) and an ordinary text PDF makes **zero** Gemini OCR/document-reading calls; a page is only sent to the model when its local text is empty/only layout noise/`(cid:…)` garbage (`classifyPageText`), and a page that renders blank is proved blank locally (`isRenderedPageBlank`) instead of being OCR'd. A PDF with no usable page at all (a scan) takes one whole-file model read; a mixed PDF keeps its local pages and recovers only the unreadable ones through the page-batch OCR path (`OCR_MAX_PAGES`/`OCR_BATCH_PAGES`). Local text is never erased by a failed fallback, and a corrupt file fails the asset (`extractState=failed` + `extractErrorCode`), never the upload. What else the model reads (`lib/native-read.js`): **images** — one picture is one page (transcription plus a line about any figure); **DOCX/PPTX** — Gemini cannot open OOXML, so the local extractor keeps the text and the *pictures inside the file* (slide screenshots, pasted scans, figures) are read in batches and merged into the slide/section they belong to, which is what makes an image-only deck readable; **TXT/MD** — the bytes are the text, no model call. Model routing falls back from `DOC_READ_MODEL` to `DOC_READ_FALLBACK_MODEL` on 404/503 only (a 429 is project-wide, so retrying another model is pointless). `NATIVE_DOC_READ=0` disables the model path everywhere. Cloudinary remains a compatibility fallback until its migration window closes. All 16 media formats are supported across ingestion: Documents (`pdf`, `docx`, `pptx`, `ppt`, `txt`, `md`), Images (`jpg`, `jpeg`, `png`, `webp`, `heic`, `heif`), and Audio (`m4a`, `mp3`, `wav`, `ogg`, `aac`).
- Extraction is verified by `npm run test:pdf` (`scripts/test-pdf-extraction.mjs`: text/scanned/mixed/blank/large/corrupt PDFs, quota failure, interrupted retry, counted model calls, LlamaParse completion/park/fallback, and the local-first rule that a text PDF makes zero provider calls), `npm run test:llamaparse` (`scripts/test-llamaparse.mjs`: REST request shapes, page mapping, error taxonomy), `npm run test:extraction` (`scripts/test-extraction-pipeline.mjs`: per-format parser checks, incl. DOCX heading/table Markdown) and `npm run test:single-pass` (`scripts/test-single-pass.mjs`: typed context on the single-pass path and the study-set condense). Pipeline reliability adds `npm run test:ai` (typed provider errors, Retry-After, deadline timeouts), `npm run test:recovery` (attempt clamping, yield/stall accounting, rate-limit delays), `npm run test:long-recovery` (hierarchical reduce: single-item skip, split-on-413, zero-call resume) and `npm run test:merge` (`scripts/test-merge-resume.mjs`: durable checkpoint-or-throw, budget yield + resume, skipped completed merges, timeout/5xx/rate-limit/auth policy, invalid-output repair then split, a 30-section document, concurrent attempts, section-level fallback), plus `npm run diagnose:jobs` for a read-only stage/checkpoint/AI-call report. None touches Postgres, Gemini, LlamaCloud or the network.
- PDF extraction depends on `@napi-rs/canvas` being imported from `src/lib/extract.js` with a *literal* specifier before `pdf-parse` is loaded: pdfjs-dist evaluates `new DOMMatrix()` at module scope, and its own `createRequire` lookup is invisible to Vercel's file tracer (missing package → `ReferenceError: DOMMatrix is not defined` at boot). Both imports must stay lazy so a missing native binary degrades PDF text to `null` instead of crashing every route on import.
- Long-running AI work runs through the Postgres queue (`src/lib/queue.js` + `src/lib/runner.js`, `FOR UPDATE SKIP LOCKED`) drained by `/api/internal/jobs/tick` (`CRON_SECRET`-authed, GET or POST; Vercel cron **daily** — Hobby plan caps crons at once/day; upgrade to Pro to tighten) plus opportunistic kicks (`triggerRunner`/`triggerExtraction` via `@vercel/functions` `waitUntil` on enqueue, upload complete and both job status polls — those kicks are the primary drain while a student is watching; the cron is the nightly janitor sweep). Free-plan caps (`FREE_MONTHLY_*`) are warn-only until billing ships. Long-file map/reduce checkpoints every digest and reduce wave (`job.checkpoint`, scoped `jsonb_set`); reduce is hierarchical with output-budgeted waves, skips a merge for single-digest sections and splits oversized waves instead of retrying them. Checkpoint writes go through `lib/job-checkpoint.js` and are **durable or throw** (`CheckpointWriteError`, retried three times, then a transient job failure) — a merge whose result is not on the row is not finished work, and swallowing the write was what kept long documents yielding at "Combining". Per-entry writes are first-write-wins (`WHERE checkpoint #> path IS NULL`), so a slower attempt adopts the newer stored value instead of overwriting it; merge batches are identified by `stableBatchId()` (scope + level + member hashes, never list position), so a resume skips every merge already stored. A merge request may only start when `REDUCE_MIN_WINDOW_MS` + `REDUCE_RESERVE_MS` of the pass is left (otherwise the job yields with ids in the yield `detail`), waves are capped by item count (`REDUCE_BATCH_ITEMS`) as well as by chars, a payload above `MERGE_PAYLOAD_MAX_CHARS` is split rather than sent, and every result is compacted to `MERGE_SHRINK_RATIO` of its input while keeping all headings, terms and formulas so the hierarchy really shrinks. A section whose merge the model cannot produce is folded locally and the note says so, but a document where more than `MAX_DEGRADED_SECTION_SHARE` of its sections had to be folded fails the job instead of reporting itself ready. Provider failures are typed (`lib/ai.js` `AiError`), a 429 is parked for its Retry-After without spending an attempt, and `jobs.heartbeatAt` plus yield/stall accounting fails a no-progress loop with a useful message instead of leaving the app on "Combining" forever. `shapeJob` exposes `stageDetail`, `progressUnit` and `heartbeatAt` additively.
- Never log or return `NEON_API_KEY`, `LLAMA_CLOUD_API_KEY`, Clerk secrets, or signed URLs beyond their TTL.
- Push delivery lives in `src/lib/push.js`: `notifyUser(userId, {title, body, mobilePath, webPath, tag, transports})` fans out to Expo Push (`push_tokens`) and Web Push/VAPID (`web_push_subscriptions`), deleting credentials the provider reports dead. It reads with direct `prisma` (cross-user infra work) and its network calls stay outside `withUser`; a failed push never fails a job. `pipeline.js` sends "study set ready" on completion, `src/lib/reminders.js` sends the **web-only** daily "cards are due" push from the jobs tick (mobile schedules that one locally), and `/api/me/push-*` + `/notification-settings` back the two settings screens. `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` are the only web credentials; without them `/me/push-status` reports `web: false` and the UI hides the toggle. Runbook: `docs/push-notifications.md`.
- The day streak is **server-authoritative app-open** activity, shared by mobile and web (migration `21_daily_streak`): `user_active_days` holds one row per user/local day and is the source of truth; `User.streakDays` / `lastActiveDay` / `streakTimezone` / `streakWarningSentFor` cache the run. `POST /api/me/activity` (`routes/me.js`) unions in today for the supplied timezone (falling back to the client's `utcOffsetMinutes` when that zone name is unusable, then UTC — a bad zone must never wedge the sync), recomputes with `lib/streak-rules.js` (`computeRunStreak`: consecutive active days ≤ 2 days apart) under a user-row lock, and prunes active days older than the 400-day recompute window in the same transaction. A gap of 3+ calendar days restarts the run at 1. `GET /api/study/home-summary` reads the cached run through `streakViewForUser`, which returns 0 when the latest active day is 3+ days old, so a missed cron can never show a stale count. The daily jobs tick calls `sendStreakNotices()` (after reminders) to push a 2-day warning and a 3+ day reset notice, each at most once per absence; its updates are conditional on the day the sweep read, so an open that lands mid-sweep wins instead of being reset, and the loop is bounded by a 45 s budget (leftovers wait for the next tick). `STREAK_NOTICES=0` disables it. Unit rules: `npm run test:streak` (`scripts/test-streak.mjs`, no network/DB).

## AI generation contract (server owns it)

`Job.kind` is one of `study_set | lecture_note | course_reference`; `Note.noteKind` is `note | reference`.

- `study_set` — summary + flashcards + quiz; note `body` untouched. Outputs strictly conform to `backend/src/config/study-pack-schema.js` (`shortSummary`, `keyTerms`, `formulas`, `examQuestions`, `flashcards`, `quiz`).
- `lecture_note` — AI rewrites `body`, original capture preserved in `transcript`, then summary + cards + quiz (typed notes included).
- `course_reference` — condensed reference sheet only, no cards/quiz. Short sources stay one page; a long chunked document becomes **one sectioned reference note** instead of failing the one-page cap.
- One upload / one job = one `Note` (the client-created id). Long documents never create `ovw_`/`part_` records: `long-doc.js` maps, reduces, writes `##` sections and updates `job.noteId` once; section bodies are checkpointed in `job.checkpoint.sectionBodies` so a yielded run resumes without re-paying for finished sections. Regenerating a job tombstones only that job's legacy `ovw_<jobId>` / `part_<jobId>_*` rows. The assembled body is notices → `## Overview` → one `##` per section → `## Key Takeaways`, and `LONG_DOC_REVISION` is part of the long-source hash.
- Context budgeting: notes must have at least 40 characters to generate. A document whose whole stored text fits `SHORT_SOURCE_CHARS` (60k) skips map/reduce entirely — `singlePassSource` in `pipeline.js` feeds the stored page rows straight to one write call, **including the note's typed body** (`assembleSource` merges it the same way; a file note the student typed context around must not lose it), and `assembledShortSource` covers a note that mixes a document with photos (pictures have no chunk rows, so the long-file path would silently drop them). The study set never reads a sliced source: material above `STUDY_SET_SOURCE_CHARS` (60k) is condensed with the same cheap-model digests the long-file path uses (`condenseMaterial` in `note-pipeline.js`, `meta.studySetCondensed`), and an unbroken paste is pre-split so it cannot become one oversized digest.
- Very large sources: the chunk target scales up to `AI_MAX_CHUNK_CHARS` (24k) so a full file lands near ~90 digest groups instead of ~150 tiny calls; more than `MAX_CHUNKS_PER_JOB` (120) groups fails early with an honest "upload in chapters" message **before** any model call. Reduce waves are sized by payload budget (`REDUCE_MAX_CHARS`, 85% margin) and oversized items are slimmed — payloads are never sliced mid-JSON. The first 429/quota error stops the map immediately: remaining parts stay unattempted and resumable.
- Validation: AI outputs undergo strict schema validation; if the first pass fails, a strict retry at temperature `0` is executed before failing.
- Persistence: flashcards and quizzes are stored in normalized relational tables (`flashcards` with SM-2 spaced repetition fields: `ease: 2.5`, `intervalDays: 0`, `reps: 0`, `dueAt: now()`, and `quizzes`/`quiz_questions`). Regeneration idempotently replaces existing cards/quizzes for the note.
- `pipeline.startAttempt` re-asserts `noteKind`; `POST /jobs` returns **409** when a non-reference kind targets a `reference` note; references increment `Usage.references`, not `summaries`.
- Client side: `Sua/src/lib/generate.ts` (`generationKindFor`, queue drain, finishers, `reconcileAiOutputs`) and `create.tsx` (`jobKindForTarget` / `noteKindForTarget`). Pending notes are synced **before** `POST /jobs` or the server 404s. Upload-triggered conversions have no local queue row, so `reconcileAiOutputs` backfills cards/quiz.
- When touching this area, update all four layers together: Prisma schema/usage, `pipeline.js`, `routes/jobs.js`, and the mobile queue/UI copy.

## Mobile conventions

- Styling: NativeWind `className` only; the `style` prop is allowed **only** on `SafeAreaView`. Colors are CSS variables declared in `Sua/tailwind.config.js` and remapped for dark mode by `Sua/src/state/appearance.tsx`; use `colors` from `Sua/src/config/theme.ts` for icon/style values instead of hex literals. Gold is fill-only (never text), one gold button per screen, 48px minimum tap targets.
- Never add or remove `--tw-*` utilities (`shadow-*`, `ring-*`, transform, gradient, `vars()`) after an element's first render: NativeWind's dev-only upgrade warning crashes with a bogus "Couldn't find a navigation context" (nativewind#1812). Keep those utilities static and toggle plain values such as `opacity-*`. Note `bg-gold/60` omits `--tw-bg-opacity` while `bg-gold` sets it, so alpha/non-alpha toggles on one element are unsafe too.
- Routes live in `Sua/src/app`; shared components/hooks/libs stay outside it. `@/*` maps to `Sua/src/*`.
- `@clerk/expo`'s `useAuth()` returns a **new `getToken` closure on every render** (its `useCallback`-free wrapper around `@clerk/react`'s memoised one, added to fill `SessionJWTCache`). Never put `getToken`/`getAuthToken` in an effect dependency array: `AppContext`'s hydration effect does the whole post-sign-in request burst (`/me`, `/courses`, note sync, per-course pulls, the offline queues), so an unstable dependency re-fires it on every render — and the burst sets state, so it re-fires itself, and the API's 10-connection pool dies with `P2028`. `AppContext` keeps Clerk's function in a ref behind a stable `useCallback` wrapper. `activeAttempt` is the second half of the guard: one burst per account at a time, with a refresh that arrives mid-burst replayed once when the attempt settles, and failures retried on the `HYDRATION_RETRY_DELAYS_MS` ladder instead of a flat 15s re-storm.
- The **hydration burst is the only place background queues may be fired**. Connectivity/foreground listeners call `requestRefresh()` and nothing else — the burst already runs `flushUploads`/`drainGenerationQueue`/`reconcileAiOutputs`/`flushStudyProgress`, and firing them from a listener too stacks a second unguarded set of transactions beside a burst still in flight. Course pulls go through `mapLimited(serverCourses, COURSE_PULL_CONCURRENCY, …)` (3, never an unbounded `Promise.all`: each pull holds one pooled connection for its whole transaction), and `POST /me/activity` runs at the burst **tail**, after the pulls settle, because it takes a lock on the user row the pulls read.
- A hydration failure has **three** verdicts, and `AppContext` keeps them separate (`authRejected`, `serverBusy`, and plain "unreachable"): 401 = the server refused this session, any 5xx (the API's capacity 503 included) = the server answered and could not do the work, no status = nothing was reached. Only the last may be reported as a connection problem — `(app)/_layout.tsx` and `auth-finish.tsx` pick their copy from those flags, and neither shows a raw `error.message`, because "Something went wrong on the server" under a banner about Wi-Fi sends students to reboot a router.
- SQLite migrations are the `MIGRATIONS` array in `Sua/src/lib/notes.ts`, tracked by `PRAGMA user_version`. Append a step; every step must be idempotent because fresh installs replay all of them and a throw retries on next launch.
- The day streak is **not** derived from SQLite (`computeStreak` is gone): `Sua/src/lib/streak.ts` queues local days in the settings KV (`app_streak_pending:<userId>`), caches the server answer (`app_streak_cache:<userId>`, per account), and syncs through `POST /me/activity`. `AppContext` owns `appStreak`/`refreshAppStreak`; Home and Study read the context value, never a local recompute. The sync is skipped when the queue is empty and today is already synced (pull-to-refresh forces it).
- Sync: the client pushes `updatedAt`; the server rejects stale writes; pulls use pending-safe upserts so a locally pending note is never clobbered. A queued local edit only owns `title`/`body` — the pipeline's outputs (`transcript`, `summary`, `aiState`, `noteKind`) are adopted from every pull, a queued upsert older than the server copy is dropped so the row can stop claiming "Waiting to sync", and an empty local body never hides server text (the server mirrors that rule: an empty push cannot wipe a stored body). Drain order is notes **then** uploads (uploads may reference an unsynced note), and the persisted Wi-Fi-only toggle must be respected. A course pull is incremental when it can be: `GET /notes/course/:id?since=` answers `{ notes, serverTime }`, and the device keeps one per-account window (`notes_pull_cursor:<userId>`) that `advanceNotesPullCursor` moves to the **earliest** reported `serverTime` minus a 2-minute margin — only after every pull **and** `pullTombstones` applied, because `updatedAt` can be another device's clock (the server accepts the pushed timestamp), so a client must never trust its own. A partial pass leaves the cursor alone and re-downloads everything next time: slow, never lossy. Callers that want a whole course (a single note screen, a generation refresh) simply omit `since`.
- Sign-out is an account switch. `signOut` (`state/AppContext.tsx`) releases the push token, flushes pending notes best-effort (5 s cap), calls Clerk, then runs `clearStudyDataForAccountSwitch(db)` (`lib/notes.ts`): every study table plus the recorded/queued media files, while `settings` keeps device preferences and per-user caches (`note_section:%` rows are dropped with their notes, along with both sync cursors — `note_tombstone_cursor%`, `notes_pull_cursor%` — because the `notes`/`note_tombstones` rows they describe no longer exist). Every sync cursor is keyed by account: the device-wide `note_tombstone_cursor` this replaced let the first student's deletion window hide the second student's own deletes, so notes their first owner had deleted came back. The wipe runs only after Clerk confirms the sign-out, so a failed sign-out never destroys local work. Account deletion still uses `wipeLocalData`, which clears `settings` too.
- Recording: 2-minute m4a segments with unique filenames; only `finalized` segments upload. On crash recovery drop the in-progress segment (truncated m4a is unplayable) and resume from the finalized ones.
- Markdown: note bodies render through the in-house subset parser (`Sua/src/components/markdown.tsx` + `lib/markdown.ts`), not a third-party renderer (React 19 compatibility); it also renders simple pipe tables. `lib/markdown.ts` owns `parseNoteSections` (fence-aware, splits only on `##`) and must stay behavior-identical to `web/lib/markdown.ts`. The editor *input* uses `react-native-enriched-markdown` (math/code/video disabled in `package.json`).
- Note reader: AI bodies page through `parseNoteSections` one section at a time (`components/note/section-reader.tsx`): TOC, Previous/Next, `(index + 1) / total` reading progress, a Finish reading state, and a 120 ms opacity fade. Position is device-local (`settings` KV key `note_section:<noteId>`) and never touches the note row or sync; AI progress stays in `AiProgressCard`. Bodies without `##` render as plain Markdown.
- Every screen must work offline except AI generation and Ask Sua.
- Notifications are opt-in and Android-first: nothing asks for permission on launch — the student turns it on in `profile/notifications.tsx`, which creates the `study` channel **before** requesting permission (Android 13 shows no prompt without a channel), then stores the Expo token in `expo_push_token` and posts it with `platform`. `push_enabled` defaults to `false`. The daily reminder is scheduled **locally** (`review_reminder_enabled` + `review_reminder_time`), so a device with an Expo token gets server pushes for generation and stays on local reminders; `generate.ts` suppresses its own "study set ready" banner when a token exists so nothing double-notifies. Taps route through `src/components/notification-observer.tsx` (cold start + running) using the server's `data.path`. Push needs a dev/release build and `google-services.json` — see `docs/push-notifications.md`.

## Web conventions (`web/`)

- Next.js **16.4** (App Router, React 19, Tailwind v4, Turbopack). Read `web/AGENTS.md` + `node_modules/next/dist/docs/` before using framework APIs — `middleware.ts` is now `proxy.ts`, and layouts use generated `LayoutProps<"/path">` types.
- **Cache Components is enabled:** any client hook reading URL data (`usePathname`, `useParams`, `useSearchParams`) needs a `<Suspense>` boundary above it or dynamic-param prerendering fails (`blocking-prerender-client-hook`). See `components/app-shell.tsx`.
- Clerk is v7 (Core 3): `<SignedIn>/<SignedOut>/<Protect>` throw in client components — use `useAuth()`. Protected routes are `/app/*`; public are `/`, `/download` (Android install page), `/health`, `/policy`, `/terms`, `/sign-in(.*)`, `/sign-up(.*)`.
- Product routes live under `web/app/app/…` so URLs read `/app/home`, `/app/note/[id]`, etc. Shared components/libs stay in `web/components` and `web/lib`; `@/*` maps to `web/*`. Note creation (`/app/create`) enforces a 40-character minimum note length for generation; Note view (`/app/note/[id]`) embeds `FlipCardViewer` on the Cards tab (3D flip reveal + SRS review launch) and `InlineQuizPlayer` on the Quiz tab with real-time answer verification, explanations, and score tracking. The Note tab renders `components/note/section-reader.tsx` when the body has `##` sections; reading position is the URL hash plus `note-section:<id>` in localStorage, and generation progress remains the separate `.ai-progress` card.
- Styling mirrors mobile tokens: CSS variables in `app/globals.css`, `colors` from `web/config/theme.ts` for JS values, screen styles in `web/app/app.css`. No hex literals in components; gold is fill-only, one gold button per screen, 48px tap targets. Tailwind utilities are fine alongside `.class` names. Keep every web route within mobile viewport widths; follow the responsive layout and overflow-audit rules in `web/AGENTS.md` and do not mask horizontal overflow on `html` or `body`.
- Data access goes through the same Express routes as mobile using `lib/api.ts` + `useApi()` (Clerk bearer token) and `useResource` for fetch-on-mount/retry. Never call Postgres directly. Web-only server reads must stay **additive** (`GET /api/study/home-summary`, `/study/sets`, `/study/due?ahead=`, `/study/quizzes/:quizId`, `/notes/:noteId`).
- Online-first by design: no offline queue, IndexedDB cache or sync layer; preferences persist in `localStorage` (`web/lib/prefs.ts`), not SQLite.
- The daily app-open streak is reported by `web/lib/activity.ts` (`ensureDailyActivity`): `components/app-shell.tsx` pings `POST /me/activity` once per account/day (localStorage `sua.activity.v1`, module-level in-flight guard) for every `/app/*` page, and the Home/Study summary loaders await it (4 s timeout) before `study.homeSummary()` so today is included. Both screens read `streakDays` from the summary; the count is the same one mobile shows.
- Note ids are client-generated (`crypto.randomUUID()`) and must be synced before `POST /jobs`; the SRS constants in `web/lib/srs.ts` must stay identical to `Sua/src/lib/srs.ts` and `backend/src/lib/srs.js`.
- Verify with `npx tsc --noEmit`, `npx eslint .`, `npm run build`.
- Web push is server-driven: `/app/notifications` (reached from Profile and Preferences) is the only place permission is requested. It stores the browser subscription via `POST /api/me/push-subscription`, saving reminders through `/api/me/notification-settings`; `lib/push.ts` holds the browser APIs and `public/sw.js` renders notifications and routes taps to the payload `url`. `next.config.ts` serves `/sw.js` uncached. The VAPID public key comes from `NEXT_PUBLIC_VAPID_PUBLIC_KEY` — when it or the server pair is missing, the toggle hides rather than failing. `app/manifest.ts` makes the app installable, which is what web push on iOS 16.4+ requires. Runbook: `docs/push-notifications.md`.

## Environment & deploy

- `backend/.env` (copy `backend/.env.example`): pooled `DATABASE_URL`, direct `DIRECT_URL`, Clerk keys + webhook secret, Neon storage (`NEON_API_KEY`, `NEON_PROJECT_ID`, `NEON_BRANCH_ID`, `NEON_STORAGE_BUCKET`), `GEMINI_API_KEY` (transcription/OCR), `LLAMA_CLOUD_API_KEY` (first PDF/DOCX/PPTX extractor; `LLAMAPARSE_ENABLED`/`LLAMAPARSE_FORMATS`/`LLAMAPARSE_TIER`/`LLAMAPARSE_VERSION`/`LLAMAPARSE_TIMEOUT_MS`/`LLAMAPARSE_MAX_ATTEMPTS` tune it), `XKIRO_API_KEY` (text generation via the OpenAI-compatible xkiro API; model from `AI_BULK_MODEL`/`AI_STRONG_MODEL`, default `qwen/qwen3.8-max:free`).
- `Sua/.env.local` (copy `Sua/.env.example`): `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY`, `EXPO_PUBLIC_API_URL`. Android emulator needs `http://10.0.2.2:4000/api`; `api.ts` falls back to that when unset. Use `https://` for any non-localhost API — Android release builds block cleartext HTTP.
- **One Clerk instance for the whole stack.** The client publishable key (`EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`) and the backend's `CLERK_PUBLISHABLE_KEY` / `CLERK_SECRET_KEY` / `CLERK_WEBHOOK_SECRET` must all come from the same Clerk instance — test and live keys are not interchangeable. A mismatch (e.g. a `pk_live_` app against a `pk_test_` API) signs the student in on the client and then answers **401 to every API call**, so hydration never resolves and `/auth-finish` dead-ends on "Connect to finish signing in". `lib/api.ts` logs that hint on a 401 in dev; `AppContext` reports the failure as `authRejected` rather than as "offline".
- Backend deploys to Vercel from `backend/` (`vercel.json` → `npm run build`); jobs drain inside the same function via opportunistic kicks plus the `/api/internal/jobs/tick` cron (daily on the Hobby plan) — there is no separate worker host and no Redis.
- The Android APK (~134 MB) is too big for a git blob (>100 MiB) and for Vercel Hobby static uploads (100 MB), so it is served **straight from a Cloudflare R2 bucket** behind `dl.<domain>/android` (no egress charge). There is no CI publishing step yet: upload with `npm run r2:upload` from `backend/`, then set `version`/`sizeLabel`/`sha256` in `web/config/download.ts`. The page's base URL comes from `NEXT_PUBLIC_ANDROID_APK_BASE_URL` or the `bucketBaseUrl` constant in that file — it never links github.com. Runbook: `docs/android-download-hosting.md`.
